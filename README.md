# AI 原生价值投资研究工作台

一句话：**把 8 年机构买方投研框架工程化、结构化，构建一套将价值投资与 AI 深度结合、可复用的开源研究工作台。**

研究链条固定为 **「来源 → 事实 → 论点 → 假设 → 估值 → 跟踪」**，换公司只换数据，不换结构。目前库内同时运行五家公司的研究底稿：长江电力（600900.SH）、太阳纸业（002078.SZ）、中国建筑（601668.SH）、腾讯音乐（01698.HK）、小米集团（01810.HK）。

## 一、为什么要做这件事（价值投资 × AI）

市面上不缺“巴菲特分身”式的提示词工具，但如果只看 AI 给的一个“低估/买入”结论，遇到长周期的股价回撤根本拿不住。对真正的价值投资者而言，**值钱的是底层的推理过程，结论只是水到渠成的副产品**。

把 AI 引入价值投资，面临一个核心矛盾：**人类的认知带宽是有限的，而 AI 的输出带宽是无限的。** 让 AI 自由发挥，10 秒就能吐出上万字看似头头是道的分析；让精力有限的人每次从零去核查 AI 无限膨胀的产出，最终只会陷入信息过载，或盲信幻觉。

因此，这套系统的核心设计思路是**用成型的买方研究框架给 AI 套上“结构化牢笼”**：

1. **往固定的格子里填东西**：哪些财报和行业数据可靠、哪些信息需要交叉验证、每一份证据该放在论证链路的哪个位置，都有明确的数据库表结构与执行标准。
2. **全链路事实溯源**：任何论点和估值假设都必须向下锚定到具体的定性事实、定量指标和原始来源文档，杜绝无据空谈。
3. **降低认知负担**：一旦熟悉这套框架，研究者就能一眼定位整个论证的信息链路，快速找到最关键的假设和分歧点，**把 AI 的无限算力，转化为人类可审查、可信任的研究杠杆**。

本项目采用公开构建（Build in Public）的方式持续迭代，记录把买方研究框架拆解为数据库、Agent 工作流与实战标的研究的全过程（GitHub：`https://github.com/lzcjsyr/value-investing`）。

## 二、怎么打开（本机 NocoBase + PostgreSQL）

五家公司统一放在 `nocobase/companies/`，各自的 `docs/` 保存研究手册，`data/` 和同级脚本用于重建公司数据，中国建筑和太阳纸业的原始资料也随公司目录保存。手册中的研究结论和数值对应撰写时点，当前工作台数据以 PostgreSQL 为准。

```sh
cd nocobase
docker compose up -d          # 先启动 Docker Desktop
```

- 网站：http://localhost:13000 （只监听本机），管理员 `admin@nocobase.com`
- 关电脑、休眠或 Docker 没启动时，网站和采集都不工作；错过的定时点不补跑
- 备份：`./backup.sh`（整库到 `backups/`）；临时查库：`./psql.sh -c "select ..."`
- 停用：`docker compose stop`

首次进入看「驾驶舱」，再看「商业模式 → 核心论点 → 假设依据 → 预测与估值（① → ⑤）」这条主链。

## 三、库里有什么

每家公司一个顶层菜单，各有一套同样的页面：

| 分组 | 页面 |
|---|---|
| 顶层 | 驾驶舱（关键读数、立即采集按钮、图表） |
| 商业模式 | 商业模式拆解、产业链与五力（含竞争对手）、竞争壁垒、风险分析、价投适配度、核心论点；可视化与明细编辑分标签 |
| 数据底稿 | 业务数据、财务数据（三大报表＋分部补充；报表里有的科目由指标按公式实时算，不另存）、定性事实（数字以外的事和外部参照）、来源文档 |
| 预测与估值 | 按「框架与后台 / 估值地基：Greenwald 三层价值」分层（2026-11-11 重构，旧估值全部删除）：① 资产价值 → ② 盈利能力 → ③ 增长价值 → ④ 独立资产 → ⑤ 股权价值，最后是假设依据。每页总览＋本层的编辑标签；第二层是一张调整后利润表（历年数→正常化值→E）；不设情景（三层本身就是从保守到乐观）；门槛（投资回报率要求）全部公司共用，在「框架与后台 / 统一设置」里调。先只做腾讯音乐，其余四家的估值输入暂时清空。本公司全部指标在「经营与财务 / 定量指标」 |
| 研究维护 | 维护研究本身：自动检查、待办清单（只放待办，判断写在核心论点）、变更日志 |
| 另外 | 顶层「宏观数据」（利率、汇率、商品，各公司订阅）；「框架与后台」（使用说明、数据结构、模型公式、公司、采集） |

表、视图和计算缓存的清单见 [数据结构说明](nocobase/framework/docs/数据结构说明.md)。输入保存在 `vi_<表>_base`，需要派生字段时增加 `vi_<表>_calc`；`vi_<表>` 是界面视图，写入由触发器落回 base。字段定义在 `framework/spec.py`，SQL 由它生成。系统内「框架与后台 / 数据结构」已补充近期变更、数据分工、两种预测与估值路径、表清单与关系图。

## 四、数据怎么连起来

```
来源文档 ──> 重要事实 ──> 商业模式拆解 / 产业链 / 竞争对手 / 竞争壁垒 / 风险分析
                  │                        │
                  └──> 核心论点 <───────────┘（壁垒与适配度都靠论点裁决）
                            │
                       假设依据 ──> 三层估值：资产负债重估（① 资产价值、④ 独立资产）
                                    ──> 盈利能力（② 盈利能力）──> 增长（③ 增长价值）──> ⑤ 股权价值
```

三条硬规矩：

1. **同一事实只存一次**（`重要事实`），其它表通过关联引用；一条事实平均被 4 张分析表引用。建立引用**不会**自动改估值数字。
2. **空白＝未知，不是 0**；现金流缺项时宁可不输出价值。比率一律存小数（0.052＝5.2%），金额单位亿元。
3. **派生值不手填**：单价、派息率、税率、利息、每股价值、检查结果都由公式算；模型表永不出现股价。

## 六、改东西之前

- **改数据**：在页面里改，或改 `companies/<代码_名称>/analysis.py`/`seed.py` 后重新生成 `seed.sql` 并执行（按业务键引用，可重复执行，只影响本公司）。
- **改结构或公式**：`framework/gen_sql.py` → `sql/01_schema.sql`（或写迁移）→ `02_calc.sql`、`03_ui.sql` → `register.py` → 重启 app → `build_pages.py`。顺序错了会出现字段说明与页面不一致、关联字段加载失败等问题，坑清单见 `framework/README.md`。
- **改页面**：`build_pages.py` / `build_overview.py` / `build_finmodel.py` / `build_chainmap.py` / `build_fitboard.py`，不要只在界面上点（重建页面会覆盖）。改前先 `./backup.sh`。

## 七、还没做完

1. **定时采集停用**：靠手动按钮；采集的新鲜度规则不统一（入库用固定 7 天，健康检查读配置）。
2. **状态语义不实**：自检会直接写「已通知」，手动流程统一标「完成」而不区分各源成败。
3. **归属规则靠约定**：公司/模型外键可空，当前模型、基准情景的唯一性没有数据库约束。
4. **年度假设的引用过宽**：50 行假设挂了 400 条假设依据引用，平均每年 8 条，尚未逐参数收敛。
5. **四家公司页面已对标长江电力**（2026-10-26）：商业模式采用可视化＋编辑标签，产业链和竞争对手合并到一页；财务模型与估值收拢重复入口。重建入口为 `framework/align_companies.py`。长江电力本次仅做水位采集诊断。
6. 少数论点没挂到任何壁垒（太阳纸业 3、中国建筑 3、小米 2、腾讯音乐 1、长江电力 1）；小米有 2 个对手没进产业链或壁垒。
7. **多业务估值**：新增业务身份，商业模式与分部估值共用；总价值分业务估值、资产估值与调整两部分。小米已落地，经营固定资产标记已含业务价值，避免再次加总。
